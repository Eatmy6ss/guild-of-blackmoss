## 页面验收结果

在独立端口 5413 使用三名 15 级人类合成队，初始金币 900、经验 0、士气 60、默契 0。真实打通前三层：金币依次 +30/+38/+45，实际种族经验 +21/+29/+38，每场士气 +6、每对幸存队友默契 +1；第三层守塔者掉落一件装备。第二层后购买第三层保险扣 120，一次购买后按钮禁用。

回城刷新后，经游戏自身导出界面核对：金币 **893**、每名成员经验 **88**/士气 **78**、每对默契 **3**、手动塔纪录 **3**、仓库新增 **1** 件，13 条编年史序号互不重复。公会随机状态为 **1831689269**，与初始 123456 发出入塔种子后的一次推进一致，塔层自身抽样不额外推进公会序列，刷新未重新抽样。

收益在原战斗状态面板汇总展示；未换皮或新增界面。页面使用键盘操作；自然阵亡、撤退和团灭未在这支强队中出现，对应结果由自动测试和实际 App 回调验证，不能称为页面手动验收。原用户 5178 页面及真实存档未写入测试数据。

## 实现落点

- `src/sim/settlement.ts`：副本/塔统一 `settleEncounter`，返回本趟、公会成员及各类后果；判断和奖励都在此。内部沿用远征推进、塔层药水/血量/奖励助手；王国在推进索引前捕获已打遭遇。App `applyOutcome` 只同步输出，UI 自动循环继续沿用原边界。
- `src/sim/run.ts` / `tower.ts`：阵亡判定统一到 `markPermadeath`，旧塔入口仅为兼容脚本的薄包装；成长统一 `settleGrowth`，保持种族经验、远征训练/等级折扣，塔层显式传原经验。每趟有 UUID 身份和独立 RNG，结算物品身份用本趟/遭遇/序号生成，重放同一输入一致。
- `loot.ts` / `rng.ts`：掉落支持显式 RNG 与可提供身份，原未提供身份的调用仍用 UUID（保持独立模块生命周期不撞 ID）；原 seed API 继续可用。`createLootRng` 复用唯一 mulberry32，`createStatefulRng.state()` 可续接。
- `chronicle.ts`：结算显式提供序号，不改变其他事件生成器的默认调用方式。App 同步完结算后接续全局序号，用即时 ref 避免同帧故事互相覆盖。升级/升星按本场前后比较，修正旧整趟快照在后续胜场反复登记旧里程碑的问题。
- `wish.ts` / `member-traits.ts` / `scars.ts`：原心愿/特性规则共用，随机数显式输入；创伤主结算同样走本趟 RNG，旧助手兼容调用以战末 RNG 状态建立确定性源。副本/塔的心愿检测保留原展示状态时点，不新增心愿或特性。
- `src/state/save.ts`：v19 只补公会 `rngState`，v18 迁移按已有时间/日期建立稳定种子，不改资产；合法状态 0 与高位保留，损坏值回退。`scripts/dev-save.ts` / `smoke.ts` 合成档补字段，旧示例档保留作迁移证据。
- `App.tsx`：招募/访客/治疗/公会事件走可保存的公会 RNG；选路、路线事件、宝箱与下一场种子走本趟 RNG。展示岔路不消耗 RNG。奖励反馈汇总金币、士气、经验、默契、阵亡/遗物/保险、装备和委托进度。
- `settlement.test.ts` / `save-rng.test.ts` 和历史 `gameplay.test.ts`：新增纯函数与迁移测试；历史界面测试使用真实的新 App 应用结果和结算回调，保留保险/重复点击/训练/稀有猎杀/宝箱/事件/保存的数值断言。

## 行为边界与文档校准

1. 高塔现在调用与副本相同的死亡冲击：同场只施加一次、每位亡者分别留史，保留勇猛/亡灵/冷静减免和与首位亡者的羁绊幅度；没有重复叠加死亡惩罚。阵亡祝福、遗物收费与下一层保险不变。
2. 塔胜场补原 `applyVictory` 的 +6 士气、存活凯歌装备的 +2（同一共享规则）；经验仍为 `20 + 8×(层−1)` 再按种族处理，不加训练场的“远征”倍率。每层幸存队友共同经历 +1 默契，撤退也记录幸存者经历、团灭无人发放。升级/升星与阵亡都留史，手动纪录限制不变。
3. 副本数值与相同抽样序列的实际旧链一致。对照不比较随机物品 ID，也不把来源改变后的历史种子当成同一抽样输入；副本 Boss 不再从会话计数器另建 RNG，而由本趟 RNG 发奖。塔的掉落也随本趟序列；概率/品质/阶级不变，但旧固定种子的物品组合可能改变。
4. 老文档的 `EncounterOutcome` 是结构草案，其中的效果类型并未定义；实际用可落地的快照与效果数组，不另造一套逐条效果处理器。App 的 source 分支只选择写回副本还是高塔状态，不再判定奖励。
5. #0.10 需要先保存 RNG，故存档 v19 已占用；#0.5 顺延 v20，#0.6 最终版本开工时再核对。不是借机实施后续装备/远征存档架构。

## 尚未覆盖与修正方向

- 自动测试和合成强队界面检查不代表自然成长胜率、全职业手感或经济平衡验收。若塔中士气/默契反馈影响体验，先收集自然挑战数据；不在本轮修改既定幅度。
- 途中刷新仍回到出征前，不保存正在进行的战斗/RNG；本趟仍有函数字段，交 #0.6 序列化。公会随机位置与资产在原安全边界同批保存。
- 物品归属仍是三处实例形态；结算身份可重放不是 #0.5 的注册表。继续 #0.5 时保持 RNG 迁移和现有唯一归属验收范围。
- 对照采集、页面导出核对和反馈截图保存在忽略目录 `.vite/settlement-qa/`（`comparison.json` / `browser-evidence.json` / `tower-feedback.png`），不作为跨机器回归工具入库；可重复的主要验收已进入测试套件。当前提交/推送/PR 状态以 HANDOFF 为准。
