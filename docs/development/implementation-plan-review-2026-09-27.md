## 对应任务开工前必须修订

### R1 · #0.1 的接口、时序和文案迁移还不完整

证据：计划第 209、236–252、307 行；`src/sim/mechanics.ts:156`；`src/data/mech-docs.ts:44`；`src/App.tsx:2078`。

- 文字要求通过 `sibling(kind)` 访问兄弟机制，但给出的 `MechanicCtx` 接口没有此字段。应补齐同一份契约。
- `intent()` 没有当前 tick，却要表达无敌状态；现有无敌机制到期不会删除 `rt.until`。应提供只读时间信息，以免界面/AI 永久误报无敌。
- 删除 `mech-docs.ts` 前，除了静态 `counter`，还必须迁移 `mechanicBrief(def)` 的参数化说明（读条时间、伤害、阈值等）。建议注册表提供 `describe(def)`，和引擎共用参数默认值解析，保留现有信息量。
- 文档称地面法术未发送 `casting`，但 `mechanics.ts:151` 已有该事件。该项应写成迁移后保留、仅发送一次，不能再补发一次。
- “最后一 tick”明确为 `until - 1`；`until` 时刻的伤害不计入已结束窗口。已有回归 `scripts/gameplay.test.ts:103` 正是这个口径。保留该边界，不顺手调整全局行动顺序。

验收补充：Boss/杂兵各覆盖读条开始、阈值不足、末 tick 达阈值、截止时刻、死亡取消；无敌到期不再提示；战术手册仍显示真实参数。

### R2 · 难度冻结与批次 0 出口必须拆开

证据：计划第 444–451、650–656 行，及 `natural-progression-measurement.md` 的同资产跨图记录。

现稿要求迁移时保持既有数值、倒挂留到批次 2 后修，同时又要求批次 0 的 I7/I7b 和全地图单调性全部通过。既有倒挂不能靠模型换名消失，这不是可同时保证的验收。

修订建议：

1. 批次 0 强制通过统一缩放、相同上下文生成一致、迁移前后数值等价等正确性检查。
2. I7/I7b 保留为目标曲线检查；已有失败用具名清单记录，只接受已登记问题、不接受新增倒挂，不删测试、不放宽阈值掩盖结果。
3. 批次 2 解冻后修正曲线，再要求目标关系全部通过。若制作人要求提前修倒挂，应明确记录为 C4 的例外，而不是让实现者自行猜测。

### R3 · 物品归属必须包含未结算战利品

证据：计划第 469、565–570、601、944 行。

#0.5 只承认装备、背包、待赎回遗物三种归属，并要求把其余“孤儿物品”放回背包；#0.6/批次 3 随后新增 `activeRun.pendingLoot.items`。照现稿组合实现，塔内存档加载时，未结算掉落可能被当作孤儿提前发放。

修订建议：从 #0.5 起将活动远征待结算池纳入合法所有者；分开定义“物品记录唯一”和“所有权引用唯一”。最近掉落提示等展示引用不算所有权。迁移还应区分旧 ID 碰撞与同一实例重复引用，不能仅凭 ID 或属性相同就判断是否复制资产。

验收补充：塔内保存/加载仍在待结算池；离塔兑现一次；团灭损失或保险补偿一次；重复加载不多发、不吞装；永久死亡转遗物后原装备位不再持有同一物品。

### R4 · 结算和随机数要作为同一次状态更新提交

证据：计划第 520–530、1072 行；`src/App.tsx:344`、`:516`；`src/sim/rng.ts:5`；`src/sim/scars.ts:69`。

将结算搬到纯函数并不能自动保留当前依靠 phase 守卫实现的“一场只结算一次”。尤其后续恢复终局战斗时，需要防止再次领取金币、经验、遗物、创伤及统计。

修订建议：

- 为遭遇和结算记录稳定身份，结算结果与“已应用”标记同次写入；重复应用同一结果应完全无效。
- RNG 保存消费后的游标，而不只是初始 seed；#0.10 引入公会随机流时就同步落盘其状态。公会、远征和战斗分别明确随机流归属，避免刷新重复抽签或基地操作影响战斗。
- 随机数清单还要覆盖 `settleScars` 的默认 `Math.random`；只搜索计划指定的三个文件不够。
- I9 不能只比较 `consequences` 的键。两边都返回空数组也会通过。应验证真实见证人的士气变化、羁绊后果和阵亡故事条目。
- “副本黄金值不变”与“换 RNG 后重录所有黄金值”拆成两项：固定随机输入下验证逻辑等价；更换随机源后验证同状态可复现。不能靠更新期望值证明搬迁正确。

验收补充：结算调用两次与一次结果相同；结算前后刷新均不重复发奖；输入状态不被意外修改；恢复后事件、创伤与掉落一致。“逐字节一致”限定为规范化的玩法结果，排除真实保存时间和纯视觉数据。

### R5 · 刷新恢复的最迟依赖时点要一致

证据：计划第 644、655、944 行。

#0.6 被允许延后至批次 4 前，但批次 3 的离塔结算已依赖它的待结算战利品；批次 0 又把刷新恢复列为强制出口。

修订建议：若允许延期，最迟必须在批次 3 开始前完成；延期的批次 0 标为“其余项目完成，序列化延期”，不能写所有出口通过。恢复测试覆盖战斗中、战斗结束待结算、休整、事件选择待确认和离塔兑现，不只任取一个节点。

### R6 · 治疗规则的现状描述有误，不能当普通整理直接实现

证据：计划第 904–910 行；`src/sim/combat.ts:1116`、`:264`。

当前药水计算为 `maxHp * HEAL_PCT * (1 + healReceived)`，实际受受疗属性影响。计划写成“不吃任何属性”，又要求未来不吃受疗，会削弱已有构筑。

另外，`mods.heal` 当前是对受疗值累加 `mods.heal - 1`，不是直接覆盖。改成独立乘区有理由，但会改变结果，应明确标为规则调整。例如受疗 +20%、治疗修正 0.5，旧倍率为 0.7，独立乘算会成为 0.6。

建议保留药水的受疗加成，新增 `healPower` 不影响药水；若要取消受疗或改变乘区，先列出前后公式、代表性装备影响，再按产品规则变更处理。技能、药水、持续治疗、吸血等路径都应明确适用范围，避免“统一入口”变成统一抹掉差异。
